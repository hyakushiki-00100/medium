# note 変換ガイド（Markdown → note 公開用）

日本語の Markdown 原稿を **note で読みやすく公開できる形**に整えるための運用ガイド。
note 公開作品は別の **NOTE チーム**が担当するため、本ガイドは引き継ぎ時の共通仕様として使う
（引き継ぎの流れは [`../handoff/README.md`](../handoff/README.md)）。

> ⚠️ note の仕様は変わりうる。ルールには**検証状況**を明記する。
> 「確信度:高」等の内部メモは本ガイド（内部文書）には残すが、**記事本文には決して残さない**
> （読者向け完成記事では確からしさを地の文で表現する。CLAUDE.md の非交渉基準）。

## 結論（先出し）

1. **表は使わない** → 箇条書きに変換する。
2. **見出しは h2 / h3 のみ**。記事タイトルは本文から分離して「タイトル欄」に入れる。
3. **水平線 `---` は使わず**、テキスト区切り `──────────` に置換する。
4. **タグは投稿画面の専用欄で入力**する。本文末尾のタグ行は参照メモにすぎない。
5. **段落はほぼ1文単位に分割し、間に空行を挟む**（オーナー提示の参考例`tanjyoubi-paradox.md`に準拠。下記参照）。
6. **空行は「完全な空行」でよい**（全角スペース1文字を挟む旧ルールはオーナー提示の参考例で不要と確認され撤回。下記参照）。
7. **HTML は note に直貼りできない**。note 用は Markdown 版を使う。HTML は独立アーカイブ用。
8. **下書き完成後に「推敲パス」を一回かける**（語尾の単調さ・間・文の長さ。下記「推敲パス」節）。
   執筆時ではなく、fact-checker の指摘を反映し終えたあとに実施する。

## 変換ルール一覧

| 項目 | note の制約 | 対応 | 検証状況 |
|---|---|---|---|
| Markdown の表 | 非対応。貼っても表にならない | 表を**箇条書き**に変換 | 複数の解説記事で一致・**確信度 高** |
| 見出しレベル | **h2・h3 のみ**対応。h1 や h4 以下は h2/h3 に丸められる | 本文は `##` / `###` のみ。大見出しは `##` で統一 | 複数の解説記事で一致・**確信度 高** |
| 記事タイトル | 本文とは別の「タイトル」入力欄がある | 本文冒頭の `#` 見出しを削除し、`【タイトル案】` として別記 | 仕様として確認・**確信度 高** |
| 水平線 `---` | 貼り付け挙動が確認できていない | 安全側に倒し `──────────`（テキスト区切り）に置換 | **未検証**（確信度 低）→ 保守的に回避 |
| タグ | 本文中の記法とは連動しない。投稿画面の専用欄で入力 | 本文末尾のタグ行は**参照メモ**として残すのみ | 仕様として確認・**確信度 高** |
| 太字 `**text**` / 箇条書き | 貼り付け後の見た目が未確認 | 使用は可。投稿後に実画面で目視確認する | **未検証** |
| 見出し・タイトルの文字サイズ | note 側テーマで固定。記事側から指定不可 | サイズ調整は諦め、`##` 統一で**一貫性**を担保 | 仕様として確認・**確信度 高** |
| 段落・改行 | モバイルで長段落が読みにくい | **ほぼ1文ごとに段落を分け**、完全な空行を挟む(2026-09-12、オーナー提示の他アカウント実例`tanjyoubi-paradox.md`に準拠して基準を引き締め) | 実際に note 投稿されている参考例と一致・**確信度 高** |
| 空行(段落間) | ~~完全な空行だとコピー&ペースト時に note 側で段落間の空白が失われることがある~~(2026-09-09時点の報告) | **完全な空行のままでよい**。オーナー提示の参考例(`tanjyoubi-paradox.md`)は完全な空行のみで構成されており、全角スペース1文字を挟む対応は不要と判明したため撤回(2026-09-12)。ただし挙動が環境・アカウントによって揺れた既知の報告があるため、貼り付け後は必ず目視確認する | 参考例で反証・**確信度 高**(以前の全角スペース対応は撤回) |

## 手順（MD 原稿 → note 投稿）

1. **原本を保存**したまま、`<slug>-note.md` として note 用コピーを作る（原本は編集記録として温存）。
2. 上表に沿って変換する:
   - 表 → 箇条書き
   - 見出し → `##` / `###` のみ
   - `---` → `──────────`
3. 本文冒頭の `#` タイトルを削除し、ファイル先頭に投稿用メモを置く:
   ```markdown
   <!--
   note 投稿手順:
   1. 「タイトル」欄に【タイトル案】を貼る
   2. 本文（この下）をコピーして貼る
   3. タグは投稿画面の専用欄で入力（本文末尾のタグ行は参照用）
   -->
   【タイトル案】〜〜〜
   ```
4. **確信度ラベルの残存ゼロ**を確認（本文に編集メモを残さない）:
   ```bash
   grep -nE '確信度|Confidence:|\(confidence' <slug>-note.md   # 0 件なら OK
   ```
5. note に貼り、**投稿画面で実際の見た目を目視確認**（太字・箇条書き・区切り線）。
6. タグを専用欄で入力し、公開。公開後に URL を記録する。

## 推敲パス（JA・下書き完成後）（2026-09-17〜、オーナー提示の編集方針より）

**位置づけ**: 執筆時のルールではなく、**fact-checker の指摘を反映し終えた JA 下書きに対して最後にかける一回のパス**。
執筆時に適用すると `article-production-standard.md` の8ビート構成と喧嘩する（ビート自体が
「読者の痛み → actionable insight」を渡すための構造で、説明を担っているため）。

オーナーから提示された「文芸的な編集」16項目のうち、**本シリーズに合う項目だけを採用**した。
採否と理由を明記しておくので、新規セッションで蒸し返さないこと。

### 採用する（下書きに対して実施）

- **語尾の単調さを崩す**。敬体で統一している都合上、地の文が「〜です。」「〜ます。」で揃いやすい。
  **同じ語尾が4つ以上続いたら原則直す**（3連続は文脈で判断）。
  ```bash
  python3 tools/check_gobi.py                    # articles/note/*-ja.md を全件
  python3 tools/check_gobi.py --min 4            # 4連続以上だけ
  python3 tools/check_gobi.py articles/note/x-ja.md
  ```
  ⚠️ **例外**: 問答の再現部分（「〜と尋ねました。」「〜と答えました。」が続く箇所）は、
  テンポが速いこと自体が読みやすさになっているため無理に崩さない。
  ⚠️ **語尾を変えるためだけの不自然な言い換えは禁止**。崩せないなら文を分ける・順序を変える・
  短い一文を独立させる、で対処する。
  ⚠️ **常体の一文を差し込んで変化をつけるのも禁止**（「〜受けている。」等）。日本語として誤りではないが、
  `article-production-standard.md` の敬体/常体の統一ルールが優先する。
  代わりに使えるのは、**疑問の断片（「どこからが雪なのか。」）と体言止め以外の分割**。
  疑問の断片は敬体チェックの許容パターンに入っている。
- **「間」を作る**。全部を等速で説明しない。要所では短い一文を独立させ、読者が一度立ち止まれる場所を作る。
  note は段落を短く切る仕様（上記「段落・改行」）と相性がよい。ただし意味のない改行は増やさない。
- **文の長さを混ぜる**。短い文・普通の文・少し長い文・会話を組み合わせる。
  全段落が同じ構造（説明→具体例→まとめ）で揃っていないか確認する。
- **整えすぎない／うまく書きすぎない**。言い切らずに終わる箇所、読者に委ねる箇所を残してよい。
  目指すのは「難しくないのに最後まで読んでしまう文章」であって、文学的に凝った文章ではない。
- **場面を見せる（限定版）**。「誰が何をした」の要約で済ませず、発言・反応・間を見せる。
  ⚠️ **ただし本シリーズでは最も危険な項目**。原典にない情景の創作（「武装した供を連れて」
  「三十年同じ木を見続け」「しばらく黙った後」等）は fact-checker がほぼ毎回検出してきた失敗の筆頭で、
  この項目はまさにその方向へ押す。**原典の字句にある要素だけを使って描写を厚くすること**。
  字句にない空気・沈黙・表情は足さない。迷ったら足さない。

### 採用しない（理由つき）

- **筆者の一人称の視点（「私には〜に思えます」等）を入れる**: `CLAUDE.md` の話者ペルソナ
  （calm / practical / secular、一人称を前に出さない）と正面から衝突する。シリーズ全体の声が変わるため不採用。
- **筆者の短い考察を追加する**: 内容の追加にあたり、語数が伸びるうえ、
  「事実と推測を混ぜない」「捏造しない」という非交渉基準との境界が曖昧になるため不採用。
- **説明を削る／教訓を押しつけない（限度付きで採用）**: 方向としては正しいが、
  職場ビート・内面ビートは装飾ではなく**商品価値そのもの**（Gumroad への導線を含む問題提起型の構造）。
  「意味の説明を先回りしない」程度に留め、ビートごと削らない。

### 重複しているため既存ドキュメントに従う項目

抽象表現の削減（「重要です」「つまり」「一方で」等）・冒頭の作り方・見出しの付け方・
不要な一文の削除・事実と創作の切り分けは、すべて
[`article-production-standard.md`](article-production-standard.md) の
「話者ペルソナ」「定型文の使い回しを避ける」「史実性の扱い」節に既にある。**そちらを唯一の出典とする**。

### EN 版との関係

このパスは **JA 版のみ**にかける。EN 版の文面は動かさない。
ただし JA だけ文体が動くと EN/JA の内容が乖離し fact-checker の照合が難しくなるため、
**事実・出典・ビートの骨格は必ず一致させたまま、語りの速度と語尾だけを動かす**こと。

## HTML について

- **note は HTML タグの直接貼り付けに非対応**（リッチテキストエディタのため、タグが文字列として表示される）。
  → 「note 用 HTML」は note 投稿には使えない。**note 投稿には Markdown 版（`-note.md`）を使う**。
- HTML 版は、見出しサイズ・行間・タイトル装飾まで自由に指定できる**独立アーカイブ / 自社サイト用**として作る。
  - カバー画像は Base64 で埋め込み、単一ファイルで完結させる。
  - 外部フォント（Google Fonts 等）を使う場合、オフラインや CDN ブロック環境では
    デフォルトフォントにフォールバックする（**未検証**の表示崩れに注意）。

## 未検証事項（要・実画面確認）

- 水平線 `---` を貼ったときの note の挙動（→ 現状は区切り線に置換して回避）。
- 太字・箇条書きの貼り付け後の見た目。
- HTML 版の外部フォント読み込みが失敗した場合の表示。
